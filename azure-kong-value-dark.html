07 / AZURE / GAP 01

現地配置を広げても管理はAzureに依存

APIM Self-hostedは現地で転送できるが、構成更新・状態報告はAzureの管理面に依存する。

接続・運用の構成例

Azure内外に接続資産を持つ場合の比較。管理通信の一時断が即座にデータ転送停止になるわけではない。

改善する点Azure中心構成の課題

Azureから管理の境界を分離

各環境のKongをKonnectで横断管理。Azureの契約・管理面に接続基盤を固定せず、クラウドや実行基盤の変更時にも管理方針を引き継げる。

転送の配置と管理の依存は別

他クラウドやオンプレにもSelf-hostedを置けるが、構成更新・状態報告はAzureのAPIM管理面へ接続。配置先を増やしても管理の選択はAzureに結び付く。

要点

実行する場所を選べても、接続管理の基準まで独立するわけではない。

09 / AZURE / GAP 02

配置先によってAI制御に差が出る

現地処理が必要な場合、Azure内のManagedで使える機能をSelf-hostedでも揃えられるかが課題になる。

接続・運用の構成例

APIM Classic/V2 ManagedとSelf-hostedの比較。Azureの全製品・全配置が非対応という主張ではない。

改善する点Azure中心構成の課題

A2Aも現地のGatewayで統制

同じ対応版のKongとAIプラグインを各環境へ配置。LLM・MCP・A2Aの接続制御と観測を揃え、配置先ごとに異なる仕組みを補う負担を抑える。

現地処理に残るAI機能差

APIMはLLM・MCP・A2Aを扱う。一方、Self-hostedはA2A専用機能が非対応。現地で同じ統制を求めると、補完の仕組みや別経路の設計が必要。

要点

同じAPI・AI接続でも、配置先で統制が分かれる場合がある。

11 / AZURE / GAP 03

MCP公開だけでは業務の結果処理が残る

API操作をMCP公開するだけの構成では、複数APIの中間結果をAIへ戻して扱うことになる。

接続・運用の構成例

標準MCPの結果をLLMへ戻す構成例。Azureに変換policyやコード実行がないという比較ではない。

改善する点Azure中心構成の課題

生成したMCP内で処理を実行

仕様からMCPサーバーを自動生成・配備。呼出し時はAIエージェントが作る処理コードを既存サーバー内で実行し、APIの中間結果をLLMに戻さず結合・集計する。

MCP公開の先の処理基盤

APIMでAPI操作をMCP公開しても、複数の結果の結合・集計をどこで扱うかは別の設計。呼出しごとに中間結果が戻ると、LLMの情報量と処理負担が増える。

要点

APIを公開できることと、必要な業務情報を返す基盤は別の役割。

Context Mesh / Kong AI Gateway
12 / AZURE / KONG SOLUTION 03

Context MeshがAPI活用を一連で提供

APIを使える形にし、必要な操作を探し、複数APIを実行・加工して必要な結果だけを返す。

接続・運用の構成例

Context MeshはAPI/MCPの生成・配備・発見・接続・加工を備える専用基盤。API認可と機微情報保護は別途設計。

改善する点Azure中心構成の課題

API活用を一連の機能で提供

API仕様・既存MCPからCode Mode MCPを生成・配備。必要なAPIを探し、呼出し時に複数APIを結合・集計し、回答に必要な結果へ加工して返す。

MCP化だけでは残るLLM負荷

MCP公開・検索と、API結果を横断する加工は別機能である。標準MCPでは中間結果がLLMへ戻り、大量データほどトークン、待ち時間、処理精度が課題になる。

要点

AIが業務APIを使いこなすための一連の仕組みを、共通基盤として提供する。
